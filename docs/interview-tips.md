# Technical interview tips

A technical interview doesn't just test whether you know the answer. It tests **how you think** and **how you communicate**. These tips are worth just as much as the technical content.

## 1. Think out loud

Talk while you think. Say what you're trying, what you expect to happen, and why you're choosing a path. The interviewer can't read your mind: if you go silent while solving, it looks like you're guessing.

> "I'm going to loop through the array with a `for` because I need to compare each element with the next one..."

## 2. Don't go silent

Long silences are your worst enemy. If you get stuck, say what you're thinking even if it isn't the final solution:

> "I'm not sure about the best approach, but I'm thinking I could start with something simple and then improve it."

Thinking out loud shows that you can reason, not just memorize.

## 3. Think before you code

Don't start writing code right away. First:

1. Restate the problem in your own words.
2. Give an example input and output.
3. Explain your plan.
4. Only then, start writing.

This keeps you from realizing halfway through that you misunderstood the problem.

## 4. Ask your questions

Asking isn't a sign of weakness; it's a sign that you think like a professional. Ask things like:

- "Does the array always contain numbers, or can it hold other types?"
- "What should happen if the input is empty?"
- "Does performance matter, or should I prioritize clarity?"

Clarifying edge cases before you code makes you look thorough.

## 5. Test with simple cases

Before you call your solution done, run through it mentally with:

- A normal case.
- An empty case (`[]`, `""`, `0`).
- An edge case (negative numbers, duplicates, a single element).

Saying "let me check with an empty case" makes a good impression.

## 6. Don't memorize without understanding

If you memorize an answer but don't understand it, any follow-up question will give you away. Understand the *why*: that's how you can answer variations you haven't seen before.

## 7. What to do when you don't know the answer

It's fine not to know something. What matters is how you react:

- **Don't fake confidence.** Good interviewers can tell.
- **Say what you do know:** "I haven't worked with that, but based on the name I'd guess it's used for..."
- **Show how you'd solve it:** "On the job I'd look it up in the docs; conceptually I think..."
- **Be honest:** "I don't know, but I'd like to learn it." That's better than a mistake delivered with confidence.

## 8. Mind the communication details

- Name your variables well (`total`, `counter`, not `x`, `a`).
- Write readable code: it's a sample of how you'll work on a team.
- When you finish, summarize: "So this function takes X, does Y, and returns Z."

## 9. After the interview

Write down the questions you couldn't answer and study them. Every interview is practice for the next one, whether you pass it or not.
